## 1. Как собирался список

`pg_stat_statements` в стеке **не установлен** (`pg_extension` — только `plpgsql`), а объём
dev-БД нерепрезентативен (самая крупная таблица — 7 тыс. строк), поэтому ранжирование по
факту замеров невозможно. Список составлен статически:

1. выбраны все места, где SQL/DQL содержит агрегацию, `DISTINCT`, `JOIN`, `IN (:list)`
   или выборку без `LIMIT`;
2. для каждого сверено фактическое покрытие индексами (`pg_indexes`);
3. спорные места проверены `EXPLAIN` на живой БД с `enable_seqscan=off` — так план
   показывает, **существует ли пригодный индекс**, независимо от объёма данных.

**Первая рекомендация вне таблицы: включить `pg_stat_statements`** (`shared_preload_libraries`)
хотя бы на stage. Без него любой такой аудит остаётся рассуждением, а не измерением.

## 3. Разбор проблемных мест и предложения

### Q2. `bids` не имеет индекса по `supplier_id` — самая дешёвая победа

`EXPLAIN` на живой БД (с `enable_seqscan=off`, чтобы показать доступные индексы):

```
Unique
  ->  Sort  (Sort Key: tender_id)
        ->  Bitmap Heap Scan on bids b
              Filter: (supplier_id = $1)
              ->  Bitmap Index Scan on idx_bids_tender_status
                    Index Cond: (status = ANY ('{submitted,admitted,rejected,winning,lost}'))
```

Планировщику нечем взять `supplier_id`: он идёт по индексу статусов, который отбирает
**почти всю таблицу** (пять из шести статусов), и фильтрует поставщика построчно.
Существующий уникальный `(tender_id, lot_id, supplier_id)` не помогает — `supplier_id`
в нём третий.

Запрос вызывается на каждый `GET /dashboard`, `GET /stats/tenders` и на каждый
`GET /tenders` со стороны участника (после задачи 11). При 300 тыс. заявок это
сканирование сотен тысяч строк на каждое открытие дашборда.

**Предложение:** индекс `idx_bids_supplier_status (supplier_id, status)`.
Одна миграция, без правок кода. Побочно ускоряет `countForSupplier` и проверки
«участвовала ли компания».

### Q3. Агрегация статусов идёт по всем тендерам компании без ограничения

`aggregatedStatusRows` делает `LEFT JOIN lots` + `STRING_AGG` + `GROUP BY` по всем
тендерам тенанта (а для участника — ещё и по всем `participating`), без `LIMIT`.
Для заказчика с 5 тыс. процедур это 5 тыс. групп и десятки тысяч строк лотов на
**каждое** открытие дашборда.

Отдельная заметка (2026-08-22): на момент первой редакции этого аудита фазы лотов
не проставлялись вовсе (лот оставался `draft` до закрытия), и агрегация почти всегда
возвращала административный статус тендера — то есть была дорогой тавтологией. Теперь
фазы ведутся (`tender-state-machine.md`, раздел 3a), агрегация работает по назначению —
и ровно поэтому её стоимость стала настоящей, а не гипотетической.

**Предложения (по возрастанию радикальности):**
1. **Материализовать** `tenders.aggregated_status` (колонка + пересчёт в
   `TenderStatusAggregator`, который уже вызывается на всех переходах) — дашборд
   и каталог читают колонку, `JOIN lots` уходит совсем.
2. Если материализация не подходит — ограничить агрегацию окном дашборда
   (только активные статусы + период), а не всей историей компании.
3. Кэшировать результат на 15–60 с в Redis: дашборд не требует секундной свежести.

Рекомендую (1): это снимает и Q3, и часть Q11, и делает сортировку/фильтрацию каталога
по агрегированному статусу возможной на стороне БД.

### Q4. Последняя ставка аукциона сортирует все ставки аукциона

```
Limit
  ->  Sort  (Sort Key: placed_at DESC, round DESC)
        ->  Index Scan using idx_auction_bids_auction_price on auction_bids b
              Index Cond: (auction_id = $1)
              Filter: (status = 'accepted')
```

Индекс даёт вход по `auction_id`, но нужного порядка в нём нет — Postgres сортирует
все ставки аукциона. `GET /auctions` делает это для каждого аукциона страницы.
При 5 млн ставок и оживлённом аукционе (тысячи ставок) это заметная работа на каждый
запрос списка.

**Предложение:** индекс `idx_auction_bids_auction_placed (auction_id, placed_at DESC, round DESC)`
— `DISTINCT ON` получает готовый порядок, сортировка исчезает. Можно частичный
(`WHERE status = 'accepted'`), это ещё и уменьшит размер индекса.

### Q5/Q6. Пагинация «выбрать всё → отрезать в памяти»

`KeysetCursor::sliceAfter` применяется в шести списках: заявки тендера, история ставок
аукциона, контракты, претензии, обеспечения, жалобы, планы закупок. Во всех случаях
репозиторий возвращает **весь набор**, а курсор режет его в PHP.

Для заявок одного тендера набор ограничен бизнесом (десятки), и это приемлемо. Опасны
два места:
- **история ставок аукциона** — на активных торгах это тысячи строк на каждый запрос
  страницы, с гидратацией сущностей;
- **контракты компании** — растёт линейно и не ограничено ничем.

**Предложение:** перевести эти два списка на настоящий keyset в SQL
(`WHERE (created_at, id) < (:cursor_created_at, :cursor_id) ORDER BY created_at DESC, id DESC LIMIT :n+1`)
— ровно так, как уже сделано в `listCatalogPage`. Остальные четыре оставить как есть
и вернуться к ним, когда наборы вырастут.

### Q7/Q8. Списки id в `IN (...)`

`idsForTenant`, `tenderIdsForSupplier`, `wonTenderIds`, `contractCustomerIds`,
`lotIdsWonBy` возвращают неограниченные списки, которые дальше уходят параметром
`IN (...)`. Для компании с тысячами процедур это тысячи параметров в запросе — растёт и
время планирования, и объём протокола.

**Предложение:** там, где обе стороны в одной БД, заменять `IN (:list)` на подзапрос
(`EXISTS (SELECT 1 FROM bids b WHERE b.tender_id = t.id AND b.supplier_id = :company AND b.status = 'winning')`).
Здесь есть цена: правило проекта запрещает модулю ходить в чужие таблицы (PHPArkitect
rule 6), а `wonTenderIds` приходит из модуля `Bid`. Поэтому **это не «просто оптимизация»,
а архитектурное решение** — либо принять read-модель, разделяемую модулями, либо оставить
списки id и ограничить их сверху. Нужно ваше решение.

Промежуточный дешёвый вариант: ограничить списки разумным потолком (например, 5 000 id)
и логировать превышение — так деградация станет видимой раньше, чем болезненной.

### Q12/Q13. Таблицы, которые никто не чистит

**`outbox_events`:** в dev уже 7 174 строки, **все** в статусе `published`. Команды
очистки нет — есть только `idempotency:cleanup`. При целевом объёме событий таблица
растёт на миллионы строк в месяц; индекс `(status, created_at)` при этом продолжает
работать, но раздувается вместе с таблицей, а `VACUUM`/бэкапы дорожают.

**`audit_log`:** append-only по требованию (FR-1.8), 6 753 строки в dev. Партиционирования
**нет вообще** — `pg_class` не содержит ни одной таблицы с `relkind='p'`, хотя
`observability.md` §4 и алерт `TenderPartitionSizeHigh` говорят о «размере партиций
(audit/auction_bids)». То есть мониторинг предполагает партиции, которых в схеме не существует.

**Предложения:**
1. `outbox:cleanup` — удаление `published` старше N дней (по образцу `idempotency:cleanup`),
   в планировщик. Ретенцию задать в env.
2. `audit_log` и `auction_bids` — партиционировать по месяцам (`RANGE (created_at)`).
   Это разовая тяжёлая миграция, её лучше делать сейчас, пока таблицы маленькие, чем
   на 20 млн строк.
3. Привести `observability.md` в соответствие: либо партиции появляются, либо алерт
   переписывается на размер обычной таблицы.

### Q1. Каталог: полнотекстовый поиск сделан через `ILIKE '%…%'`

Фильтр `q` разворачивается в `LOWER(number) LIKE '%…%' OR LOWER(title) LIKE '%…%' OR
LOWER(description) LIKE '%…%'`. Ведущий `%` делает любой btree бесполезным — при
непустом `q` каталог читается целиком. Сейчас это незаметно, на 10 тыс. тендеров с
описаниями — уже секунды.

Фильтр `region` — та же картина (`LIKE '%…%'`). Фильтр `okpd2` префиксный, ему btree
пригодился бы, но индекса по `okpd2` нет.

**Предложения:**
1. `tsvector`-колонка (`number || title || description`) + GIN-индекс, поиск через
   `@@ plainto_tsquery` — правильное решение для `q`;
2. дешёвая альтернатива, если полнотекст пока не нужен: расширение `pg_trgm` + GIN
   по трём полям — `ILIKE '%…%'` начнёт пользоваться индексом без правок кода запроса;
3. `region` — привести к справочнику (или `citext` + btree) вместо поиска подстроки;
4. `okpd2` — btree по `LOWER(okpd2)` под префиксный поиск (`text_pattern_ops`).

### Q11. `stats/tenders` без индекса по периоду

`factsByDimension` фильтрует `tenant_id` + `created_at BETWEEN`. Ведущего индекса
`(tenant_id, created_at)` нет — есть `(tenant_id, created_at DESC, id DESC)`
(`idx_tenders_catalog_created`), и он подойдёт. Отдельного индекса не требуется —
пункт оставлен, чтобы не искать его заново.
